CLI, Configuration, and Storage

A command-line interface should adapt inputs and outputs while application services own crawling, indexing, and retrieval. Configuration precedence and error channels are public behavior.

Command boundaries

The flat crawl command remains compatible with existing URL and config flags. The crawlforge index subcommand crawls a site into a local context database, while crawlforge search queries an existing database. CLI code parses values and serializes results; it does not reimplement ContextEngine.

crawlforge index https://docs.example.test \
  --database .crawlforge/index.db --max-pages 100
crawlforge search "retry policy" \
  --database .crawlforge/index.db --limit 5

Help output describes only available behavior and exits without opening storage or making network requests.

Configuration precedence

Explicit command-line flags override values loaded from a configuration file; omitted flags retain file values; remaining fields use documented defaults. Validation happens after merging so an invalid effective timeout, concurrency, domain rule, or output path produces one precise error.

  • CLI value: highest precedence.
  • Configuration file value: middle precedence.
  • Built-in default: lowest precedence.

Sensitive values are not echoed in diagnostics. Relative paths are resolved according to the command’s documented working-directory contract.

Storage backends

DataStorage defines the crawl-record boundary. JSONStorage, SQLiteStorage, and asynchronous text storage preserve crawl output with backend-specific durability. They are separate from SQLiteContextIndex, which supports FTS5 search and replaceable document chunks.

Storage resources have explicit open, flush, and close ownership. A partial write must not be reported as a complete crawl record. The CLI closes the selected backend on success, expected failure, and cancellation.

Error and output channels

Machine-readable JSON is written to standard output. Logs, warnings, and actionable diagnostics are written to standard error. Expected failures such as a missing database, corrupt schema, database is locked, invalid limit, or unavailable FTS5 exit with status 2 and no traceback.

$ crawlforge search "timeouts" --database missing.db
error: context database does not exist
# exit status: 2

Unexpected internal errors retain diagnostic context for operators, but ordinary users should not receive secrets or raw storage internals. A failed command must not emit plausible success JSON.
