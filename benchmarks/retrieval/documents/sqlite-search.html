SQLite FTS5 Index Design

A retrieval index has different ownership and update semantics from an append-only crawl archive. Keeping those stores separate makes migration, replacement, and lexical ranking explicit.

Storage separation

SQLiteStorage preserves crawl records for later inspection; it is not a search index. SQLiteContextIndex owns normalized documents, chunks, provenance, and the FTS5 projection used by retrieval. Re-indexing a page may replace stale chunks without rewriting the crawl archive.

  • The archive answers “what was crawled?”
  • The context index answers “which complete chunk matches this query?”
  • Shared SQLite technology does not make the two schemas interchangeable.

This boundary also allows JSON or asynchronous text archives to feed the same local retrieval index.

FTS5 virtual table

The chunk_fts FTS5 virtual table indexes title, heading text, and chunk content. Metadata and authoritative source rows remain in ordinary tables. Search joins an FTS row back to its chunk rather than treating the virtual table as the source of provenance.

SELECT chunk_id, bm25(chunk_fts) AS raw_score
FROM chunk_fts
WHERE chunk_fts MATCH ?
ORDER BY raw_score ASC
LIMIT ?;

If SQLite lacks the extension, initialization raises FTS5UnavailableError with a concise corrective message. Silently falling back to substring scanning would change relevance and performance semantics.

Schema migrations

A small context_schema_version table records the installed schema. Migration from version 1 to version 2 runs inside a transaction, creates new structures, backfills materialized provenance, verifies required rows, and advances the version only after success.

BEGIN IMMEDIATE;
-- create, copy, verify
UPDATE context_schema_version SET version = 2;
COMMIT;

An unknown future version is rejected instead of guessed. A failed migration rolls back so the previous readable schema remains intact; a second startup can retry deterministically.

Transactions and provenance

Batch indexing writes document content, chunk rows, FTS entries, and chunk_provenance in one transaction. Either the new document view is complete or none of it becomes visible. Content hashes deduplicate identical chunk text while provenance keeps every source URL and heading path that produced it.

Readers should never observe an FTS match whose source row has already been deleted. Foreign keys, deterministic deletion order, and a single transaction protect that invariant. A locked database is reported to the caller; it is not “fixed” by dropping tables or discarding history.
