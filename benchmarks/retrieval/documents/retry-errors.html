Retries, Errors, and Backoff

Retries are a policy for specific temporary failures, not a generic loop around every exception. A sound policy preserves the final error and limits the extra load it creates.

Error taxonomy

RetryStrategy distinguishes TransientError from PermanentError. Connection resets, selected server failures, and HTTP 429 can be transient. Invalid URLs, disallowed network targets, parsing contracts, and ordinary HTTP 4xx responses are permanent unless an explicit rule says otherwise.

if isinstance(error, PermanentError):
    raise error
if attempt == max_retries:
    raise error

ParseError should not be silently reclassified as a network failure. The category controls retry behavior and gives operators a stable failure reason.

Exponential backoff

Exponential backoff grows a base delay by the attempt number and caps the result. Jitter spreads clients that failed at the same moment. A typical calculation is min(max_delay, base_delay * 2 ** attempt) plus a bounded random component.

  • The first attempt has no retry sleep.
  • The attempt counter advances only after a failed request.
  • Cancellation during sleep stops the retry loop immediately.

The retry loop shares the whole-operation timeout budget. Backoff does not grant a new unlimited deadline.

Retry-After handling

For HTTP 429, a valid Retry-After header can specify either delta seconds or an HTTP date. The crawler waits for at least that server delay, subject to its configured cap and remaining operation deadline. Ordinary exponential backoff still supplies a floor when the header is absent.

Retry-After: 7

An invalid or past Retry-After value is ignored and the normal backoff is used. Negative delays never move the monotonic schedule backward. Header parsing errors remain local policy details rather than new crawl failures.

Retry observability

ErrorRecord and RetryStats should capture the request category, attempt count, chosen delay, and final disposition without logging response bodies or credentials. The last meaningful error is more useful than a generic “retries exhausted” wrapper.

  • Count retries separately from initial requests.
  • Record whether Retry-After changed the delay.
  • Expose terminal and recovered failures independently.

Metrics explain load and latency, while structured errors explain what the caller can correct.
