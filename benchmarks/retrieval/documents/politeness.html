Rate Limits and Robots Policy

Polite crawling combines capacity, time, and authorization. A concurrency semaphore limits simultaneous requests, while a rate limiter spaces their start times and robots.txt decides whether a path may be fetched.

Rate slots

RateLimiter assigns request slots per canonical origin. A caller waits for capacity before recording its slot; recording first and then waiting can reserve time for a request that is cancelled before it starts. Slots use a monotonic clock so wall-clock adjustments do not create bursts.

await limiter.acquire(origin)
try:
    await request(url)
finally:
    limiter.release(origin)

Minimum delay, configured jitter, and server guidance all contribute to the next eligible start time. Rate slots apply to direct pages, redirect hops, and robots.txt requests.

Robots decisions

RobotsParser evaluates the selected User-Agent group and the normalized percent-encoded path. The most specific matching Allow or Disallow rule wins. Authorization and server failures while fetching robots.txt fail closed; an ordinary missing robots.txt permits crawling.

  • 404 or 410 means no published restriction.
  • 401, 403, 429, and server errors do not imply permission.
  • Network failure does not silently bypass an existing policy.

This distinction prevents “robots policy unavailable” from becoming accidental authorization.

Crawl-delay scheduling

A matching robots.txt Crawl-delay sets a per-origin minimum interval between request starts. It is combined with the configured minimum delay by taking the stricter value, then bounded jitter may be added. Crawl-delay is not a sleep after a response; slow responses already consume time but do not redefine the next reserved start slot.

User-agent: *
Crawl-delay: 2.5

Robots scheduling and Retry-After address different signals. Crawl-delay is a standing origin policy, whereas Retry-After reacts to a particular response.

Origin-scoped robots cache

Robots rules are cached by scheme, canonical host, and effective port. Two hosts with similar names do not share authorization, and HTTP rules do not automatically authorize HTTPS. A bounded time-to-live permits policy refresh without fetching robots.txt for every page.

Concurrent cache misses for the same origin should share one in-flight fetch. A failed or cancelled refresh must wake waiters with the same safe decision and must not leave a permanent “loading” entry. Redirects taken by the robots request pass through the same network and allowed-domain checks as page redirects.
